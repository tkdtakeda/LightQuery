# 進め方.md

## 1. この文書の目的

この文書は、新しいシステムや画面を設計・実装・改善するときの進め方を定める。

目的は、単に見た目のよい画面を作ることではない。

利用者が、

- 次に何をすればよいか迷わない
- 必要な情報を探し回らない
- 操作方法を覚えなくても使える
- 状態や結果を理解しやすい
- 誤操作から容易に復帰できる

ことを重視する。

そのため、特に以下を評価の中心とする。

1. 認知コストの低さ
2. ユーザビリティの高さ
3. 情報と操作の優先順位の明確さ
4. 一連の作業の自然さ
5. 状態・結果・次の操作の分かりやすさ

この文書だけで作業方針、評価方法、再評価条件、終了条件まで判断できるものとする。
他の進め方や評価基準を前提としない。

# 2. 基本原則

## 2.1 最初にレイアウトを決め、その後に機能を組み込む

最初から機能実装を進めてはならない。

まず、主要な情報、操作、画面遷移を整理し、レイアウトとして成立させる。

原則として、

1. 要求を理解する
2. 必要な作業の流れを整理する
3. レイアウト案を作る
4. 評価して採用案を決める
5. 採用案を必要に応じて改善する
6. 機能を組み込む
7. 実際の状態で確認する

の順に進める。

## 2.2 利用者の仕事を基準にする

システム内部の構造ではなく、利用者が実際に行う仕事を基準として画面を構成する。

データ構造、内部処理、開発上の都合をそのまま画面構成に反映してはならない。

画面を見た利用者が、

- 今どこにいるか
- 何が終わっているか
- 次に何をするか
- 問題がある場合は何を直せばよいか

を理解できることを優先する。

## 2.3 主操作と補助操作を区別する

その時点で利用者が行うべき主な操作を明確にする。

主操作と、

- 設定
- 管理
- 出力
- 補助機能
- 例外対応

などを同じ強さで表示しない。

選択肢を増やすことではなく、判断しなければならないことを減らすことを優先する。

## 2.4 評価のための評価をしない

評価にはコストがある。

品質向上につながらない案の再生成、全面再評価、同じ指摘の再検討を繰り返してはならない。

最初は広く探索し、一度方向を決めた後は、採用案を狭く深く改善する。

# 3. 最初に要求を整理する

レイアウトを作る前に、要求から以下を整理する。

- 利用者が達成したい最終目的
- 最初に行う操作
- 主な作業の順番
- 各段階で必要になる情報
- 各段階で行う主操作
- エラー、未完了、未一致などの例外状態
- 作業完了後に得る結果
- 頻繁に行う操作
- ときどきしか使用しない操作

不明点があっても、合理的に判断できる範囲では作業を止めない。

仮定した内容は記録し、後から変更可能な構造とする。

# 4. レイアウト案を5案作る

## 4.1 5案作成の目的

初期レイアウトは5案作成する。

5案を作る目的は、似た画面を5個作ることではない。

同じ要求に対して、異なる設計上の仮説を探索するためである。

## 4.2 5案は意図的に違わせる

5案それぞれに、異なる設計上の考え方を持たせる。

例えば、

- 作業手順の理解を優先する
- 主操作への到達性を優先する
- 情報の一覧性を優先する
- 情報量を減らす
- 画面遷移を減らす

などが考えられる。

ただし、この分類を毎回固定して使用してはならない。

対象となるシステムの目的と要求を分析し、そのシステムに有効と思われる異なる設計思想を選択すること。

## 4.3 似た案を量産しない

案Aを作り、それを少し変更してB、C、D、Eとする方法は禁止する。

各案は、

「この構成にすると利用者の負担を減らせるのではないか」

という異なる仮説を持つこと。

各案について、その案で何を改善しようとしているのかを短く説明できるようにする。

## 4.4 この段階では本格的な配線をしない

初期案は静的HTML、モック、またはそれに相当する軽量な方法で作る。

評価前に本処理との本格的な接続を行わない。

捨てる可能性のある案に対して、データ処理や複雑な機能実装を行わない。

# 5. 5案を同じ基準で評価する

5案を作った後、全案を同一の評価基準で比較する。

可能であれば、案を作った役割とは別の評価役が評価する。

重要なのは、

「認知コストを重視した案だから高得点」

とすることではない。

どの設計思想で作った案であっても、完成した画面を同じ物差しで評価する。

# 6. 評価基準

## 6.1 認知コスト

利用者が理解・記憶・判断しなければならない量が少ないかを評価する。

確認する内容：

- 次に何をすればよいか分かるか
- 現在の状態を理解できるか
- 必要な情報を探し回らなくてよいか
- 前の画面の情報を覚えておく必要がないか
- 同じ意味のものが異なる名前で表示されていないか
- 不要な選択肢が判断を増やしていないか
- 説明を読まなくても主要操作を推測できるか

## 6.2 ユーザビリティ

実際に作業するときの使いやすさを評価する。

確認する内容：

- 主操作を見つけやすいか
- 操作順序が自然か
- 押した結果を予測できるか
- 作業を戻ったり行き来したりする必要が少ないか
- エラーや未完了状態から復帰しやすいか
- 不要な操作回数がないか
- よく使う操作ほど実行しやすい位置にあるか

## 6.3 情報設計

画面に表示される情報の優先順位を評価する。

確認する内容：

- 重要情報が先に見えるか
- 補助情報が主情報を邪魔していないか
- 情報量が多すぎないか
- 同じ情報を複数箇所に不必要に表示していないか
- 表、説明、ステータスなどの役割が明確か

## 6.4 作業フロー

画面単体ではなく、一連の仕事として評価する。

確認する内容：

- 開始から完了まで自然につながっているか
- 画面間で手順名や意味が変化していないか
- 次の工程への移動方法が明確か
- 途中状態からでも適切な工程に進めるか
- 完了した工程と未完了の工程を区別できるか

## 6.5 一貫性

確認する内容：

- 同じ意味の操作が同じ表現になっているか
- 同じ状態が同じ見え方になっているか
- ボタン、リンク、選択などの役割を判断できるか
- 画面ごとに操作方法を覚え直す必要がないか

# 7. 採用案を決定する

5案を同じ評価役・同じ評価基準で比較し、最良案を1案選択する。

点数だけでなく、

- 重大な問題
- 改善可能な問題
- その案固有の利点

も記録する。

# 8. 評価結果の扱い

採用候補の評価結果は次のように扱う。

## 80点以上

採用する。

重大な問題がなければ次工程へ進む。

## 70～79点

5案を作り直さない。

最良案を採用候補とし、評価で指摘された問題だけを改善する。

改善後、必要な部分を再評価する。

## 60～69点

採用候補の主要な問題を修正し、再評価する。

構造そのものに問題がなければ、5案すべてを作り直してはならない。

## 59点以下

レイアウトの基本構造自体に問題がある可能性が高いため、構成を見直す。

必要であれば5案の探索からやり直す。

# 9. 点数より優先する重大問題

次の問題がある場合、点数だけを理由に採用してはならない。

- 主要な作業経路が途中で切れている
- 主操作が判別できない
- 必要な操作に到達できない
- 操作順が実際の業務と矛盾している
- 状態を誤認する可能性が高い
- 誤操作につながる構成になっている
- 問題発生後の復帰経路がない
- 標準的な対象画面幅で重要情報が使用できない

重大問題は必ず修正する。

# 10. 5案を何度も作り直さない

初回の探索後は、

5案 → 5案 → 5案

のような再生成を行わない。

原則は、

5案
↓
比較評価
↓
最良の1案
↓
指摘箇所を改善
↓
必要な部分だけ再評価

とする。

広く探索するのは最初の1回とし、その後は選択した案を改善する。

ただし、採用候補の基本構造そのものが成立しない場合は、この限りではない。

# 11. 採用案を決めてから機能を組み込む

レイアウトの方向性が決まったら、本処理との接続を行う。

既存システムを改修する場合は、既存機能を不必要に壊さない。

機能を組み込む際も、内部処理の都合によって採用レイアウトを不用意に崩さない。

やむを得ず構造変更が必要な場合は、その理由を記録する。

# 12. 機能組み込み後の評価

機能実装後に、実際の操作として確認する。

この段階では、静的レイアウトの美しさだけを再評価するのではなく、

- 一連の作業が最後まで完了できるか
- 主操作が状態に応じて正しいか
- 押せない場合に理由が分かるか
- エラーや未完了から復帰できるか
- データの有無によって不自然な状態にならないか
- 重要な操作が必要な画面幅で使用できるか
- 補助操作が主操作を邪魔していないか

を確認する。

機能組み込み後の全体評価は原則1回とする。

# 13. 修正規模によって再評価方法を変える

すべての修正について全体評価を繰り返してはならない。

## 13.1 軽微な修正

例：

- 文字サイズ
- 文字色
- 余白
- 列幅
- 枠線
- 背景色
- 点線表示
- 補足文言
- 0件表示の改善
- 小さな位置調整

確認方法：

- 修正箇所の実画面確認
- 関連テスト
- 必要な回帰確認

原則として独立評価役による全面再評価は行わない。

## 13.2 中規模な修正

例：

- ボタン位置の変更
- 状態表示方法の変更
- 表やサイド領域の再構成
- 一部の操作経路の変更
- 情報の優先順位の変更

確認方法：

変更した画面、変更した状態、影響を受ける前後の操作だけを再評価する。

無関係な画面まで全面的に再評価しない。

## 13.3 大規模な修正

例：

- 作業手順の変更
- 主操作の変更
- ナビゲーション構造の変更
- 画面間のつながりの変更
- レイアウトの基本構造変更

確認方法：

全体評価を行う。

ただし、初期の5案作成まで戻るのは、既存の採用案の基本構造では解決できない場合に限る。

# 14. 残件管理

評価で発見した問題を、毎回最初から再判断してはならない。

各残件に状態を持たせる。

使用する状態：

- `open`
  - 未対応。対応を検討する。

- `partial`
  - 一部対応済み。残った部分を検討する。

- `resolved`
  - 解決済み。通常は再検討しない。

- `accepted`
  - 意図的にそのままとする。理由を記録する。

- `blocked`
  - 環境、外部部品などの理由で現在確認できない。

- `separate`
  - 今回の作業範囲ではなく、別作業として扱う。

通常の追加改善では、原則として `open` と `partial` だけを対象とする。

`accepted`、`blocked`、`separate` を毎回再検討してトークンや作業時間を消費してはならない。

# 15. 残件に記録する内容

少なくとも以下を記録する。

- 内容
- 状態
- 判断理由
- 利用者への影響
- 実施した対応
- 確認方法
- 再検討が必要になる条件

意図して残したものと、単なる未対応を明確に区別する。

# 16. 自動テストと実画面確認

自動テストだけで完成と判断してはならない。

同様に、実画面を目視しただけで既存機能が維持されていると判断してはならない。

可能な範囲で、

1. 自動テスト
2. 実際の画面
3. 主要な利用状態
4. 主要な作業経路

を確認する。

# 17. 代表的な状態を確認する

すべての組み合わせを人間が目視する必要はない。

その代わり、

- 初期状態
- データが存在する状態
- 正常に途中まで進んだ状態
- 完了状態
- 未一致、エラー、未完了などの問題状態
- データが0件になる状態

など、挙動が変わる代表的な状態を確認する。

画面幅についても、対象環境で重要となる幅を確認する。

# 18. 評価終了条件

次をすべて満たした時点で、評価を終了する。

- 重大な問題が残っていない
- 主要な作業経路を開始から完了まで実行できる
- 主操作が明確である
- 問題発生時の復帰方法が分かる
- 対象とする画面幅で重要情報が使用できる
- 必要な自動テストが成功している
- 未対応項目が残件として記録されている

軽微な問題が残っていることだけを理由に、評価・修正を無限に継続してはならない。

# 19. 作業結果の報告

作業完了時は、少なくとも以下を報告する。

## 実施したこと

何を変更したかを、利用者から見た変化として説明する。

## 評価結果

- 5案をどのような考え方で分けたか
- どの案を採用したか
- 採用理由
- 主な評価結果
- 改善を行った場合はその内容

を記録する。

## 確認結果

- 自動テスト
- 実画面確認
- 確認した代表状態
- 確認した画面条件

などを記録する。

## 残件

未対応、意図的に残したもの、環境上確認できなかったものを区別する。

# 20. 最終原則

この進め方で最も重要なのは、

「多く作り、多く評価すること」

ではない。

最初に異なる可能性を十分に探索し、その後は有力な案に集中して改善することを重視する。

したがって、

**広く探索するのは最初の1回。  
5案を同じ基準で比較する。  
最良案を選んだ後は、その案だけを改善する。  
変更の大きさに応じて評価の強度を変える。  
重大な問題がなくなったら評価を終了する。**

ことを基本とする。

最終的な判断基準は常に、

**利用者の認知コストが低く、ユーザビリティが高く、仕事の流れを自然に理解・実行できるか**

である。
